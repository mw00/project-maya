# Web localization

Settings → General → Language selects English or Simplified Chinese. The preference is stored in this browser as
`maya.language`. English is the default and the fallback for missing translations. Switching languages re-renders
existing controls; it does not reload the page, rewrite chat records, or change a model's parameters.

## Translation boundaries

`i18n.js` is the single translation entry point, with page catalogs in `i18n-*.js`. `t(key, english, values)` and
`tr(english, values)` run where product text is rendered or an action creates a UI message. Named `{placeholders}`
interpolate values without using ICU or adding dependencies. Catalogs retain the English source, and placeholders
must match in both languages. DOM traversal and post-render text replacement are not used.

User instructions, chat text, model/tool output, model IDs and quant names, paths, shell examples, environment values,
raw backend errors, report/log contents and upstream release notes remain data. Only known finite UI statuses are
localized; unknown API/finish/status values retain their original text. Measurements, formulas, API payloads and
engine flags are unchanged. English technical names and units such as DSpark, MTP, KV, GB and tok/s remain where useful.
Client-generated persistent errors carry an `errorUI` source key and values; the original diagnostic stays in `error`.
This lets an existing answer follow a language change without guessing which arbitrary backend messages to translate.
Older unmarked diagnostics remain unchanged. Short-lived notifications keep the language in which the event occurred.

## Checks

From the repository root:

```sh
node serve/test_web_i18n.mjs
python -m unittest serve.test_server.WebApp -v
git -c core.whitespace=cr-at-eol diff --check
```

The Node checks cover locale selection/persistence, English fallback, missing keys, catalog placeholder parity,
static source-phrase coverage, non-empty toast rendering and updating an existing answer after a language change.
They also cover every model family's thinking labels/tooltips, known server phases, long-answer Markdown cache locale
changes, code-wrap accessibility state, raw backend diagnostics and preserving partial model text in exports.
WebApp checks serve the real static modules through a mock engine and exercise the existing web integration paths.
There is no frontend bundler/typecheck pipeline for these checked-in ES modules; changed modules are checked with
`node --check`.

Browser acceptance uses the real page modules with disposable local API fixtures. It checks navigation, controls,
language restoration/persistence, representative page states and screenshots. Fixture measurements are invented;
these checks do not establish model quality, inference performance, hardware stability or production readiness.
Mobile drawer focus returns through a stable `data-open-chats` marker so changing an accessible label does not
break keyboard focus restoration.

The remaining-page acceptance runner is `maya/web_i18n_remaining_20261104/preview_server.py` from the enclosing
framework workspace. It uses `127.0.0.1:8097` and a separate browser origin. Its synthetic SSE responses exercise
chat and tool rendering without calling an engine. The record and screenshots are beside that script in
`ACCEPTANCE.md`; the earlier Settings/Monitor/Models record remains in `maya/web_i18n_browser_20261104/`.
