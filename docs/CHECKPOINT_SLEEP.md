# CUDA checkpoint sleep

Set `"deep_sleep": "checkpoint"` in the run configuration (the default is `"off"`; `true` and `"auto"` also select checkpoint). On Linux with a CUDA driver exposing process checkpoint, `POST /sleep` checkpoints the idle engine and releases its CUDA state. The engine process, CPU-resident weights, parallel slots and conversation state remain in RAM; the driver stores a host copy of GPU allocations, so additional host RAM is required. `POST /wake` restores the checkpoint without reloading weights. A generation request also wakes it automatically. Wake can fail when GPU memory is unavailable; in that case the checkpoint remains asleep and can be retried.

Sleep returns `409 {"status":"busy"}` if any request is running or queued. `POST /sleep?wait=30` waits up to 30 seconds (maximum 300). An unavailable CUDA checkpoint or an external vision helper returns 501 unsupported. If the engine has exited, sleep returns 409 not loaded; this does not assert that all GPU allocations have already disappeared. The built-in DeepSeek and MiniMax vision towers are part of the engine process; external vision helpers are not checkpointed and are refused. `/health` reports `loaded` and `asleep`. Shutdown or unload of a sleeping engine terminates the checkpointed process; a subsequent request then performs a full load.

CUDA checkpoint support depends on the driver and workload. There is no guaranteed wake time or GPU-memory saving until validated on the target system. CUDA graph/cache behavior and output equivalence across sleep and wake require workload-specific testing.
