# Project Maya 的 GLM-5.3-Flash 量化方案

<p align="center"><a href="QUANT-PLAN.md">English</a> | 简体中文</p>

两个自研量化版本，从官方权重制作，采用带误差反馈的舍入与按我们的硬件规模定制的 scale 精修：

| | Maya-S（先做） | Maya-L（后做） |
|---|---|---|
| 面向 | 内存池（内存与显存合计）较小的电脑（32 GB 内存即可运行，其余从固态硬盘流式读取） | 质量优先：更大的内存池 |
| 体积 | ~80-85 GB（专家约 74-78 GB） | ~135-145 GB（约 3.5 bits/weight） |
| 质量目标 | 在 ~2 bits 允许的范围内尽量贴近 FP8 模型；不出现死循环 | 对 FP8 模型 KL <= 0.05 |
| 对比对象 | FP8 模型（Z.ai 发布版） | FP8 模型（Z.ai 发布版） |

## 我们从什么出发

- **来源**：`zai-org/GLM-5.3-Flash`：62 个 safetensors 分片，**328.4 GB**，分块 FP8（e4m3 权重，每
  128x128 块一个 fp32 scale）。这是 Z.ai 自己的部署精度，所以相对 BF16 没有任何损失。BF16 仓库
  （640 GB）用不上。
- **模型**：45 层。前 3 层是稠密的（FFN 12288）；其余 42 层是 MoE，每层 288 个路由专家（top-8，
  4096 x 2048，gate/up/down）外加一个共享专家。注意力为 34 层 KDA（线性）层和 11 层 DSA/MLA 层。
  有 mHC 四流残差和一个 NextN（MTP）层。路由专家占 321B 参数中的 304.4B；单个专家为 25.2M 参数。
- **引擎当前的开发用文件**（在 Maya 自研量化之前）：一个 1.6-bit GGUF，专家部分约 84 GB。

## 机器

- **EVO-X5（2026-10-07 到货）**：Ryzen AI Max+ 495，16 核，RDNA 3.5 40-CU GPU，192 GB 统一内存
  （最多 160 GB 给 GPU），2-4 TB Gen4 NVMe。它承担重活：一层 MoE 的 BF16 是 14.5 GB，所以一层、它的
  Hessian 和校准激活能同时放下。BF16 在这里原生支持（V100 没有）。需要 ROCm 版 PyTorch（gfx1151 档）；
  先确认这个。
- **Mercury / Uranus**：引擎一侧。
  - 在我们的引擎里给每个候选量化打分（`STRATA_GLM_SCORE`：NLL、困惑度、top-1，以及对一份参考 dump
    的 KL）。
  - 为新类型补内核。
  - 测速度。

## 流水线

### 0. 拉取（下载需所有者同意）

- 62 个分片加上 config 和 tokenizer，放到 EVO-X5 的 NVMe 上，支持断点续传。
- 每个文件与 Hugging Face 的 LFS sha256 核对。
- 时间取决于带宽：1 Gbit/s 约 45 分钟，100 Mbit/s 约 7.5 小时。

### 1. 校准与评测文本

约 1M 校准 token 外加 100k 留出评测 token，全部用 GLM 的聊天模板，模型会思考的地方带思考痕迹：

- **聊天**：
  - 多轮对话
  - 指令与写作
  - 英语、葡萄牙语（巴西）、西班牙语、中文和另外几种
- **代码**：
  - Python、JS/TS、C/C++、Rust、Go、SQL、shell
  - 代码推理痕迹
- **数学与科学推理**（长 `<think>` 痕迹）
- **工具调用 / JSON / agent 回合**（GLM 的 `<|observation>` turns）
- **长文档**：几个 16k-32k token 的样本，因为 KDA 状态和 DSA 选择在长文档下表现不同
- **所有者自己的使用数据**（如果愿意纳入）：控制台的对话，或只要路由画像（`expert_usage.txt`）

公开数据集会在下载任何东西之前，先列出确切的文件与大小。自生成数据（用我们当前引擎回答约 500 条写好的
提示）用来填补聊天格式的空缺。

### 2. 参考与统计 pass

在 EVO-X5 上用 PyTorch，逐层进行，FP8 反量化到 BF16。每层只读一次，并把每个 token 的层间隐状态保留下来
（约 1M x 4 流 x 4096 x 2 B = 32 GB）。参考前向用 `transformers` 自己的 `glm5_next` 代码（5.16+），先在
几条提示上与我们的引擎核对。

每层记录：

- **每个专家的激活统计**：
  - 对角线，即 imatrix
  - gate/up（4096^2）与 down（2048^2）输入的完整 X^T X Hessian，以 fp32 累加并保存在 NVMe 上
    （全部专家约 1 TB，所以每层的用完即弃，再做下一层）
- **每个专家的路由统计**：
  - 频率
  - REAP 显著性（router 权重 x ||专家输出||，在路由到它的 token 上取平均）
  - 按领域分别统计同样的量
- **参考**：对评测 token，每个位置最终 logits 的 top-64 log-prob 加 logsumexp。这就是 KL 的标尺，格式为
  `STRATA_GLM_SCORE_REF` 所读的那种（扩展到 top-k）。

估算：约 1 小时计算（18B 激活参数 x 1M token；Hessian 累加），外加把 328 GB 读一遍。

### 3. 候选

每个张量在每个候选 GGUF 类型下用**带误差反馈的舍入**量化：

- **方法**：在完整 Hessian 上做 GPTQ，逐块进行。每块内部，由 llama.cpp 自己的量化器选 scale 和格点，
  以逆 Hessian 对角线加权。该块的误差随后传播到剩余的列。这对标量 K-quant 和 IQ 格类型都成立，因为
  块就是块。
- **候选**：
  - 路由专家：IQ1_M、IQ2_XXS、IQ2_XS、IQ2_S、IQ3_XXS、IQ3_S、IQ4_XS
  - 其余全部：Q4_K、Q5_K、Q6_K、Q8_0
- **记录**：每个（张量，类型）以及每个专家组的 Hessian 加权输出误差。
- **成本控制**：误差表每层只需抽样一些专家（288 个里约 32 个）。只有最终装配才量化全部。
- **Gumbel-softmax 精修**：论文里对格点选择与 scale 的 Gumbel-softmax 训练，其发表对象是标量 K-quant。
  它是分配结果选中 K-quant 张量之后的后加项，只有能实测降低 KL 才保留。

### 4. 分配（RCO 风格）

- **目标**：在字节预算下为每个张量选类型，最小化预测的端到端损伤（每个张量的误差乘以其层的敏感度，
  敏感度来自小规模扰动实验）。然后在我们引擎里对最好的 2-3 个分配方案与 FP8 参考打分，保留最好的。
  真正的 RCO 用真实 KL 的梯度；这里用实测误差加实测 KL 校验来近似它。
- **Maya 特有：按专家分配位数。** 我们的引擎加载自己的 pack，所以专家不必都用同一类型。
  - 热门专家（路由频率与显著性都高）拿更多位数；长尾拿更少。
  - GGUF 版本保持每张量一个类型，以便仍能装进 llama.cpp。
  - 真实文本上的使用非常偏斜（这就是 Mercury 显存层命中率能到 97% 的原因），所以按专家分配位数应该是
    每 GB 买到质量最多的一招。
- **防死循环与漂移的固定下限。** 这些部分总共只有约 6 GB：
  - 注意力、MLA、KDA 与共享专家用 Q6_K-Q8_0
  - 3 个稠密层用 Q8_0
  - 输出头 Q6_K 或更好，embedding Q6_K
  - 同一专家的 down 永不低于 gate/up

### 5. 剪枝研究（仅 Maya-S）

剪枝能腾出字节，但不是免费的：

- OpenMOSE 对这个模型做的 REAP 剪枝（每层 288 个专家删掉 60 个）实测对原模型 KL 0.45，困惑度 +2.8%。
- 公开的 3.5 -> 3.0 bit 一档大约花 0.07 KL。

所以：在 0%、约 10%、约 20% 剪枝率上做预算对齐的实验，各自把腾出的字节换成位数，用 KL、任务检查和
死循环测试评判。我的预期是轻度或不做剪枝胜出，干活的是按专家分配位数。

### 6. 装配

- **GGUF**：标准类型，每张量一个类型，可装进 llama.cpp。元数据取自当前的 GGUF。
- **Maya pack**：我们引擎加载的东西，包括用到的按专家类型。
- **视觉**：mmproj 保持 BF16（1.2 GB），等引擎支持视觉的那天用。

### 7. 评测（每个候选，同一批文本）

- **对 FP8 参考的 KL**，加困惑度与 top-1 一致率：
  - 在留出混合集上
  - 聊天、代码、数学、葡萄牙语分别统计
  - 长上下文（16-32k）
- **死循环测试**：默认采样（T=1.0，top-p 0.95）下 50 次长生成，贪心 20 次。度量重复 n-gram、永不结束的
  运行、以及坏掉的思考块结构。
- **对 FP8 模型的任务精度**（零样本 ARC-Easy/Challenge、HellaSwag、WinoGrande、PIQA，按
  lm-evaluation-harness 的打分方式：tools/maya_quant/zs_*.py），外加抽查：
  - GSM8K（100 题）
  - HumanEval 子集
  - IFEval 子集
  - MMLU-Pro（300 题）
  - 一个葡萄牙语聊天集
- **速度**：在 Uranus（64 + 32）和 Mercury 上。

## 引擎工作（Mercury/Uranus）

- **2026-10-06 已完成：解码内核**——IQ2_XS 17、IQ2_S 22、IQ3_S 21、IQ1_M 29，加上已有的 IQ2_XXS 16、
  IQ3_XXS 18、IQ1_S 19、IQ4_XS 23、Q2_K 10、Q3_K 11。
  - 在合成专家上对照双精度参考检查：每个类型都落在同样的约 1.5%（专家内核）与约 0.9%（稠密 GEMV），
    这部分来自 q8_1 激活。
  - 提示路径的 MMQ 现在也能构建 Q2_K-Q6_K。
  - CPU 通道走 ggml，覆盖所有类型。
- **llama.cpp 里没有 IQ1_M 的 MMQ**，所以它的一层走不了批量提示路径。除非那条路径加上反量化加 GEMM 的
  后备方案，否则它留在候选之外。
- 轻量内核（提示路径里稀疏路由的专家）仍只覆盖 16/18/19。其他走 MMQ——正确，但只有几行时更慢。
- 按专家类型：路由把它的 8 个专家按类型分组，逐组启动。
- KL 参考做成 top-k log-prob，这样 EVO-X5 上的参考可以在 V100 上打分。

## 所有者对主打量化的要求（2026-10-06）

- **在最小体积下尽可能贴近 FP8，不死循环，不输出坏内容。** 训练后处理在范围内：
  - 先做误差校正舍入。
  - 然后，在测量仍显示损伤的地方，对量化后的 scale 与格点选择做按块/按专家的输出匹配精修，并对小的
    浮点部分针对 FP8 教师的输出做一轮短蒸馏。
  - 每个候选都要通过死循环测试，才能称为 release。
- **在 Uranus 上制作**（EVO-X5 晚到一天）：
  - FP8 源权重在它的 PCIe 4 NVMe 上，64 GB 内存放校准激活。
  - V100 做统计 pass；它的 CPU 加 Mercury 的做量化。
  - Mercury 测双卡场景。
- **视觉：** release 带上视觉塔。
  - FP8 checkpoint 的 347 个视觉张量转成 mmproj GGUF（BF16；Q8_0 作为选项测过）。
  - 引擎的 GLM 视觉路径是 release 项目之一。
- **校准与评测向社区基准测试加权：** 单文件 HTML/CSS/JS 页面、three.js 场景与 canvas/WebGL 动画
  （含 shader），与聊天、代码、数学、工具调用、葡萄牙语、长文档并列。
  - 相关的专家据此测量并分配位数。
  - 评测加入 three.js / HTML 生成提示：页面能否解析并运行（无头浏览器）、不死循环。
- **QA：上下文填满测试。**
  - 用真实文本把上下文填到配置上限（32k，然后 64k / 128k）并持续生成。
  - 检查回答保持连贯、不崩溃、内存不超预算。
  - 路线图后段：多个上下文长度下的速度，发布在仓库里。
