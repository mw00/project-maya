# DS4.1 Flash on four RTX 4090s: v1.1.41 configuration and HTTP observations

Measurements started on **2026-10-30 at 12:40:07 UTC** (20:40:07 UTC+8), after a configuration deployment.
The operator observed higher speed in use; this note shares the operating configuration and the recorded measurements.
**No controlled, per-parameter A/B was performed.** It does not attribute a gain to NUMA permissions, any one setting,
or the engine version. The [earlier v1.1.35 case study](ds41-four-4090-20261029.md) remains a separate, differently
shaped workload; its numbers must not be used as this run's before arm.

All **27 formal request records** are in the [sanitized JSON](ds41-four-4090-v1141-20261030.json). One 32-token-limit warm-up ran first,
but its result was not saved. This publication reused existing records and read-only inspections: it ran no new
inference, restarted no service and changed no production configuration. It is separate from `maya.sh --bench`
and the README's official speed tables.

  The on-host source archive has no Git metadata. Its `ds4_main.cpp`, `ds4_model.cu` and `ds4_model.hpp` matched

- A deployment acceptance record before the run and a later read-only audit matched the runtime configuration and

## Configuration actually in use

This is an excerpt of the observed native command, **not a complete server deployment file**. Placeholders replace
private locations; authentication and host-specific mount/setup details are intentionally outside the example.

```sh
maya-ds4 --serve \
  --pack '<PACK_DIR>' --gpus 0,1,2,3 --max-context 262144 \
  --tp 2 --layer-split auto --prefill-chunk 8192 --reserve-mib 1536 \
  --mmap-experts auto --dspark on --expert-profile '<EXPERT_PROFILE>' \
  --vision off --parallel 8
```

The corresponding explicit environment was:

```text
DS4_ENGRAM_RAM=1
DS4_REQUIRE_ALL_RAM=0
STRATA_DS4_SLOT_KEEP=1
STRATA_DS4_SLOT_CAP=16
STRATA_DS4_SLOT_RAM_GB=24
STRATA_DS4_SLOT_DIR=<PRIVATE_SLOT_DIR>
MAYA_ENGINE_STALL_S=600
MAYA_REQUEST_QUIET_S=600
MAYA_GLM_RESPONSES_JOB_TIMEOUT_S=600
```

These are the literal names used by this v1.1.41 deployment; consult [SETTINGS.md](../SETTINGS.md) for aliases in
other versions. Container `CapAdd` included `SYS_NICE`; privileged mode was off and Docker's default seccomp profile
was retained. No explicit cpuset CPU/memory binding was supplied. Host `kernel.numa_balancing` remained **1**;
no explicit HugeTLB pool was reserved. Service defaults were temperature 0, top-p 0.95, reasoning effort `none`.
Total context was 262,144; the service's default output limit was 32,768, overridden by every measured request.

Startup and acceptance records showed:

- **Requested TP2 fell back to effective TP1**, with each GPU holding its own layers. Four GPUs were used; this is
  not a functioning four-GPU tensor-parallel group.
- Two full Engram tables locked: **110.595 decimal GB**. All **8001 CPU-lane experts** were copied into RAM:
  **68.8 decimal GB**, **two NUMA parts**, **80 CPU threads**. This was the observed outcome of `--mmap-experts auto`,
  not a guarantee that it will fit on another machine; `DS4_REQUIRE_ALL_RAM=0` does not enforce all-RAM placement.
- **8 native conversations**, **16 parked RAM slots**, and a **24 GiB slot budget** are different limits. The slot
  budget is not a preallocation or a hard bound on serialization peaks. The deployment acceptance recorded zero
  `set_mempolicy`/`mbind` failure messages after the replacement started; it did not measure their performance effect.

`DS4_HC_FUSE`, `DS4_DECODE_TRIM`, `DS4_ROUTE_FUSE`, `DS4_ENGRAM_PREFETCH` and `DS4_DRAFT_COST` were **not enabled**.
There was no override for the DSpark cumulative threshold or `DS4_COPY_NUMA`. No `--suffix-draft` argument was set
(the v1.1.41 default is 3). These unmodified/default mechanisms must not be presented as newly applied optimizations.
The configuration did **not** reduce native parallelism to 4, expand the RAM-slot budget to 36 GiB, or disable host
NUMA balancing. A proposed tuning recipe containing those changes was not the measured configuration.

## Recorded performance

### Repeated short prompt: three runs per output limit

Every request had **42 input tokens**. The exact same quantum-computing prompt was repeated, first three times at
128 output tokens, then three times at 256. Only the very first request reported no cached input tokens.

| Output limit | Runs | Median native decode, tok/s | Median TTFT, s | Cached input tokens, in run order |
|---|---|---|---|---|
| 128 | 3 | 80.2 | 0.0466 | 0, 41, 41 |
| 256 | 3 | 87.6 | 0.0247 | 41, 41, 41 |

The first uncached 128-output request was **68.7 tok/s native decode**, **0.6481 s TTFT**; its two repeats were
80.2 and 85.9 tok/s. The three 256-output runs were 86.7, 87.6 and 93.6 tok/s, all with 41 cached input tokens.
Thus the small median TTFT values above describe repeated/warm prompts, not generic cold-first-token latency.
Native decode excludes prefill; per-request end-to-end output rates are separately included in the JSON.

### Context scaling: one request per length

Each request returned 128 completion tokens and reported zero cached input tokens. Targets were approximate:
the runner made at most one prompt-length adjustment, so use the **actual** counts when interpreting the rates.

| Target input | Actual input | Output | TTFT, s | Native prefill, tok/s | Native decode, tok/s |
|---|---|---|---|---|---|
| 2048 | 1926 | 128 | 2.8280 | 682.0 | 69.9 |
| 8192 | 8071 | 128 | 6.4521 | 1252.1 | 68.4 |
| 32768 | 32646 | 128 | 11.6052 | 2819.4 | 67.3 |

These are KV-cold observations within an already-running process, not cold model/filesystem measurements.
64K, 128K and 256K were **not measured in this run**, despite the configured 262,144-token context capacity.

### One A → B → exact A cache-return sequence

Both synthetic prompts had 8101 input tokens and a 64-token output limit. A was replayed unchanged after B.

| Request | Input | Output | Cached input | TTFT, s | Native decode, tok/s |
|---|---|---|---|---|---|
| cold_A | 8101 | 64 | 0 | 5.6317 | 86.9 |
| interleaved_B | 8101 | 64 | 0 | 5.5795 | 83.3 |
| warm_A | 8101 | 64 | 8100 | 0.0534 | 93.9 |

The return reported **8100 cached tokens** and **0.0534 s TTFT**, versus 5.6317 s for the first A. This is one
observed reuse sequence; it does not establish an eviction/capacity result or isolate which cache tier produced the
benefit. The cached return's native prefill rate covers only the remaining work, not all 8101 input tokens.

### Client concurrency on the same native parallel=8 service

Each request had **43 input tokens** and returned **128 output tokens**. There was **one batch per client count**,
in order 1, 2, 4, 8. Native `--parallel` stayed **8 throughout**; this was not a native parallel=4 versus 8 A/B.

| HTTP clients | Output tokens | Batch wall, s | Aggregate output, tok/s | Mean TTFT, s | Requests with KV hits |
|---|---|---|---|---|---|
| 1 | 128 | 2.2451 | 57.01 | 0.5703 | 0/1 |
| 2 | 256 | 2.8417 | 90.09 | 0.3191 | 1/2 |
| 4 | 512 | 4.5046 | 113.66 | 0.5881 | 2/4 |
| 8 | 1024 | 6.9561 | 147.21 | 0.7488 | 4/8 |

Aggregate throughput is total output divided by whole-batch wall time, including client scheduling, queueing,
prefill and generation. The client-ID suffixes were reused across batches, and later batches contain a mixture of
zero and 42 cached tokens. These warm-state differences limit scaling interpretation. This short-input workload is
not comparable to the earlier case study's 8000-input-token concurrent requests. At most eight requests cannot
establish tail latency: the original runner's interpolated `p95_ttft_s` values are deliberately not published as
percentile evidence; all per-request TTFT values and batch means remain available.

## Protocol and limits

- HTTP streaming `/v1/chat/completions`; client location was not retained; temperature 0 and `stream_options.include_usage=true`.
  There was no explicit request seed, reasoning-effort or top-p override; the latter two inherited service defaults.
- TTFT starts at dispatch and ends at the first nonempty **content or reasoning_content** chunk. It is not necessarily
  the first final-answer token. Native prefill/decode rates come from response timing fields, not input divided by TTFT.
- Execution order was warm-up → six short requests → three context requests → A-B-A → client batches 1/2/4/8.
  Inter-case sleeps and token-count probes were outside individual request timers. The runner did not change service parameters; other traffic was not isolated by the runner.
- The JSON includes synthetic prompt definitions and the one-adjustment filler algorithm. The existing offline
  `http_bench_inputs.py` helper belongs to the older case study and is **not** an exact replay tool for this protocol.
  These definitions aid independent reconstruction, not bit-for-bit output reproduction.
- All 27 recorded usage objects reported the requested completion-token count. The runner did **not** persist
  output text/hashes, finish reasons or terminal-SSE receipts. Token counts alone do not prove output equivalence,
  tool correctness or successful stream termination; no full functional-suite pass is claimed.
- Initial/final status samples recorded aggregate GPU use **93,285 / 93,287 MiB of 98,256 MiB** and host use
  **196.7 / 196.9 GiB of 251.3 GiB**. They are endpoint samples, not peak memory monitoring or zero-OOM proof.
- No per-parameter causal A/B, 16-client run, long-context capacity acceptance, forced slot eviction, tool/image/API
  regression suite, or output-quality evaluation was performed by this benchmark. Version, cache history and
  workloads differ from earlier runs; no percentage speedup is attributed to a single change.

This case contributes a configuration example and an auditable observation set. It does not request changing
upstream defaults, establish a 95–105 tok/s general guarantee, or claim that the configuration is universally optimal.
