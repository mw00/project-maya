# DS4.1 Flash IQ2_XXS on four RTX 4090s: bounded HTTP tuning observations

Historical measurements from October 28–29, 2026, shared with [Issue #637](https://github.com/mw00/project-maya/issues/637).
These are configuration observations, not an engine patch or a completed deployment acceptance.
They use a different protocol from `maya.sh --bench`; do not put these rates into the README's official speed tables.
No engine source was modified for the measurements. This contribution adds documentation, sanitized numeric evidence,
and an input helper extracted afterward from the measured runner. The new helper was checked offline; it did not run the historical requests.

## Machine, model and provenance

- Model: `DeepSeek-V4.1-Flash-1017-GSQ-RCO-IQ2_XXS`; HTTP model alias `deepseek-v4.1-flash`.
- Four RTX 4090s (24,564 MiB each), 265 W per card, driver 595.99.02; two Xeon Platinum 8380s, 80 physical cores / 160 threads.
- Host memory: 269,833,428,992 bytes (251.3 GiB). Container memory limit: 245 GiB in the seven-arm phase.
- Main weights on rotational SAS behind PERC, not SSD. All seven arms had the full Engram table locked in RAM.
- Total native context 262,144; application default output 32,768, explicitly overridden to 128/256 in measured requests; vision off.
- Candidate Maya v1.1.35: `e16dec85abf8801a4cfc086ee4814071a3ff54a2`; llama.cpp `3cf03257f219afbe7334045ff7c6a06ac68c627d`.
  Matching Python server and native binary were upgraded together, so this is not a binary-only comparison.
- Original native SHA-256: `39cbff79f6431335f746ceae1fe6fb920553c813e5989b1eb0a0d2cb0fce13a8` (source revision unknown).
  Candidate native SHA-256: `4f02746386e08154b4112ca13ee2597d1fdebe1d195b049ca596d00cbf9edbfa`.
- Historical runner SHA-256: `9148fc493438c1982ce78e40d61d999125b9a3a05305e9a4cfee72cc5faf5fb3`.
  Public numeric rows and additional provenance are in the [companion JSON](ds41-four-4090-20261029.json).

These versions describe the measurements, not the current latest release. The report is submitted against a later `main`.

## Phase 1: Engram RAM observation (separate protocol)

There were 32 formal requests per arm, plus one candidate functional probe. The RAM arm locked
110,595,297,280 bytes of Engram tables (~110.6 GB / 103.0 GiB). The container limit also changed from 220 to 245 GiB.
The runs were not interleaved; expert learning, file cache, NUMA placement and warm state were not controlled.

| Metric | Original | Engram RAM arm |
|---|---:|---:|
| 128-output-token decode median, tok/s | 16.0 | 56.4 |
| 256-output-token decode median, tok/s | 16.9 | 66.5 |
| Short-request TTFT median, s | 1.331 | 0.916 |
| Long-request TTFT median, s | 1.120 | 0.701 |
| 2K prefill median, tok/s | 955.7 | 1260.7 |
| 8K prefill median, tok/s | 2090.4 | 2414.7 |
| 32K prefill median, tok/s | 3372.9 | 3734.9 |
| 16-client batch output / wall time, tok/s | 18.343 | 55.122 |
| 16-client TTFT p50 / p95, s | 59.791 / 99.042 | 19.764 / 33.322 |

The 16 HTTP clients were queued behind **one native generation lane**, with only 72–77 input tokens and 128 output
tokens each (2048 output tokens total). This is not the four-client 8000-input-token workload below.
Only 10 of 32 paired output hashes matched; 22 differed. Matched work does not establish output equivalence:
the strict comparison is **inconclusive**, and these observations do not isolate a causal 3–4x Engram-only gain.
One earlier candidate was stopped by a memory guard before optimized inference; its controlled stop is not evidence of an OOM.

## Phase 2: seven completed arms, 75 formal requests

All arms had `DS4_ENGRAM_RAM=1`. Historical common flags included `--gpus 0,1,2,3 --max-context 262144`,
`--prefill-chunk 8192 --reserve-mib 1536 --mmap-experts auto --dspark on --vision off`.
Requested `--tp 2` fell back to effective TP1 with layer splitting across all four cards; it was not a working TP2 group.

| Arm | Direct reference | Change from reference |
|---|---|---|
| original_control | — | Already-running original native/server pair, native parallelism 1 |
| official_native_control | original_control | v1.1.35 native + matching server, native parallelism 1 |
| session_cache | official_native_control | `STRATA_DS4_SLOT_KEEP=1`, `STRATA_DS4_SLOT_CAP=16`, `STRATA_DS4_SLOT_RAM_GB=24`; fresh private slot directory |
| parallel2 | session_cache | `--parallel 2` |
| parallel4 | parallel2 | `--parallel 4` |
| reserve700 | session_cache | `--reserve-mib 700`, native parallelism 1 |
| prefill16384 | session_cache | `--prefill-chunk 16384`, native parallelism 1 |

Names above are literal settings used by the historical build. Current documentation prefers `MAYA_*` over legacy
`STRATA_*` aliases; consult [SETTINGS.md](../SETTINGS.md) for the version being run. A 24 GiB session-cache budget is a ceiling,
not an allocation. Sixteen parked sessions are not sixteen simultaneous native generations. Session snapshots and
Engram lookup caching are different mechanisms.

|---|---:|---:|---:|
| original_control | 69.10 | 28.320 | 32.320 |
| official_native_control | 58.40 | 26.412 | 34.406 |
| session_cache | 64.65 | 28.664 | 32.031 |
| parallel2 | 64.70 | 30.124 | 27.390 |
| parallel4 | 60.25 | 32.412 | 20.774 |
| reserve700 | 63.20 | 27.819 | 32.990 |

- Session cache, A(8000) → B(32000) → exact A: first TTFT **5.201 s**, return **0.064 s**, **7999 cached tokens**.
  This supports a cache-return benefit for that sequence; a forced five-conversation eviction test and full slot-capacity acceptance were not run.
- Parallel4 versus parallel2: observed batch throughput +7.59%, four-sample p95 -24.15%, screening decode median -6.88%.
  Parallel4's screening median was 12.81% below the original control, exceeding the predeclared 10% regression guard.
  Parallel2 ranked as the balanced candidate, but was not finally accepted or deployed.
- Reserve700 left only **416–422 MiB** minimum sampled free VRAM and showed no measured batch gain. No recommendation to reduce further to 500 MiB follows.
- Prefill16384 on the same 32000-input/256-output screening case increased TTFT **9.788 → 13.629 s** and reduced native prefill **3283.3 → 2355.4 tok/s**.
  Resident GPU experts changed **7693 → 6838**; larger buffers displacing experts is a plausible explanation, not a profiled root cause.
  Startup to functional readiness was **1250.5 s**, versus roughly 615–760 s for the other candidate loads.

## Protocol and reuse of the inputs

The measured runner used synthetic marker retrieval followed by an essay, temperature 0, thinking off,
a fixed request seed, and streaming usage. Each screening suite had two 256-input/128-output requests,
then 8000-input/256-output and 32000-input/256-output requests. The four-client batch dispatched four distinct
8000-input/256-output requests simultaneously after calibrating their token counts.

- TTFT: client monotonic time from request dispatch to first nonempty content SSE, including queueing.
- Prefill and decode: native response timing fields, **not** input tokens divided by TTFT.
- Batch throughput: actual 1024 output tokens divided by whole batch wall time, including queue/prefill/decode.
- Screening decode median: median across the four fixed screening cases, not a generic single-stream rate.
- Four-sample p95: nearest-rank maximum of four samples, not a reliable fleet latency percentile.
- `/api/tokens` calibration preceded timing (at most four count-only probes, tolerance +/-8, observed exact target counts).
  It warms the tokenizer. “Cold” here means no reported KV/session hit, not a cold filesystem or tokenizer.
- Client ran on the inference host; LAN/WAN transfer latency was not measured. No generation retries or best-of selection.

Print the historical workload plan without contacting a server:

```sh
python tools/http_bench_inputs.py --suite screening
python tools/http_bench_inputs.py --suite contexts
python -m unittest discover -s tools -p 'test_http_bench_inputs.py'
```

`tools/http_bench_inputs.py` exposes `synthetic_prompt`, `request_payload`, and `calibrate_prompt` for an existing HTTP harness.
Supply a counter with `count_tokens(payload)` returning exact `/api/tokens` JSON (`tokens`, `approximate: false`, optional `max_context`).
The helper has no transport, authentication, deployment control, or generation loop. It rejects approximate counts;
this validation is stricter than the original helper's integer coercion, while the recorded exact counts are compatible.
Hash payloads with `sha(json.dumps(payload, separators=(",", ":")))`. The offline fixture checks the historical `short_1`
prompt and payload hashes. For `cache_A_repeat`, reuse A's **exact calibrated payload**, rather than making a new case marker.
An independent runner must also implement SSE timing, native timing extraction, actual usage checks, resource limits,
and its own safe maintenance window. The input helper alone cannot reproduce the full timing experiment.

## Comparability and acceptance limits

All 54 common request pairs matched input/payload hashes, input token counts and output work; **all 54 output hashes differed**.
Marker checks and expected completion lengths passed, but there was no comprehensive quality or determinism evaluation.
Cache-disabled controls also produced different output hashes on exact A replays, so output divergence cannot be assigned to RAM session caching alone.

Pre-batch histories differed: original/native/cache ran screening → A-B-A → batch; parallel2/4 ran screening → batch;
reserve700/prefill16384 ran screening → two long contexts → batch. Candidates started with the same initial expert-profile
hash and empty private slot directories, but the original was already warm and candidates were freshly reloaded.
Thus matched payloads are not full-state, interleaved single-factor A/B proof; small differences are observational.

The seven-arm matrix completed 75 formal requests plus six functional probes. An orchestration recovery-time reserve stopped
the workflow before the ranked candidate's final reload and acceptance, not because a Maya inference failed.
The original Maya service was restored; no extra post-restore generation was sent at the window boundary.
Final six-context replay, forced five-conversation eviction and 16-slot capacity acceptance remain **not completed**.
DSpark confidence 0.65 was skipped for the time budget; stream-thread/Engram-thread sweeps were not run.
Host-pinned all-reduce was not a proven opportunity with effective TP1; the pack already used a five-token draft block,
so a `DS4_DSPARK_MAX=5` override was not an established new optimization.

Sampled GPU temperature peaks were 64/69/68/64 C; minimum host available memory 43.23 GiB; no OOM was observed in phase 2.
These samples are not continuous full-load or failure-injection acceptance. No new GPU experiment was run for this documentation PR.
